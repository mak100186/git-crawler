# ADR-007: LM Studio as the Local LLM Runtime Engine

> Status: ACCEPTED
> Date: 2026-07-28
> Architecture: docs/architecture.md (v2)

## Context

ADR-001 established that repository summaries are generated by a local/self-hosted LLM runtime,
accessed through the `IRepositorySummarizer` abstraction, without committing to a specific runtime
engine (it used "e.g. Ollama" only as an illustrative example, not a firm pick). The Summarizer
component (Architecture §3) and self-hosted Docker Compose deployment (ADR-002) need a concrete
engine to run against.

## Decision

The local LLM runtime engine is LM Studio, run as its own container/process in the self-hosted
deployment and called by the Summarizer through `IRepositorySummarizer`.

## Alternatives Considered

| Option | Why not chosen |
|--------|-----------------|
| Ollama | Was the illustrative example in ADR-001, but the operator's explicit preference is LM Studio; no functional requirement forces Ollama specifically, and `IRepositorySummarizer` isolates the rest of the system from this choice either way. |
| Raw llama.cpp (no runtime wrapper) | Would require building and maintaining model-serving, request-queuing, and API-surface concerns that LM Studio already provides, for no benefit given the abstraction already isolates callers from the runtime's internals. |

## Consequences

- The Summarizer's `IRepositorySummarizer` implementation targets LM Studio's local API
  (OpenAI-compatible endpoint), keeping the integration surface small.
- LM Studio's model management (download, load/unload, resource limits) becomes the operator's
  primary lever for tuning the seconds-per-repo target in NFR-001, and the input to the
  benchmarking spike already flagged as risk A2.
- Does not change any consequence already accepted in ADR-001 (no per-call cost, content stays
  on self-hosted infra, operator owns inference infra) — this ADR only pins down which engine
  fulfills that decision.
